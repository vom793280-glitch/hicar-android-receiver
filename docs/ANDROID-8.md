# 安卓 8.1 车机适配说明（0.12.0）

## 0.19 换画质档后触屏失灵 —— 坐标系错位（2026-11-20 21:41）

用户反馈：切到 800×480 以外的画质档后触屏点不到。这是我引入的回归 bug。

### 根因

UIBC 触摸坐标空间是**协议固定 800×480**：
- `UiInput.encode()` 把 x/y 用 putShort 发出，且校验 `x<800 && y<480`（`UiInputTest` 向量 `001f01df`=799,479）
- `InputRouter.map()` 把触点归一化到 800×480，`touch()` 范围检查也是 800×480

0.14 我加画质档时把 `his_video_formats` 的 `scr-w/scr-h` 和 `width/height` 改成了
1280×720 / 1920×1080，还把 TextureView 的 onMeasure 宽高比改成 16:9。
手机端按更大的屏幕/画面坐标解释触点，而我方 UIBC 报文仍是 800×480 → 触点落点全错。

### 修复（保留清晰度提升，消除坐标错位）

**所有档位分辨率固定 800×480**（scr-w/scr-h/width/height 全部不变），
只提高**码率**来改善清晰度（2M / 4M / 6M，压缩损失更小）：
- `VideoQuality.formats()`：三档都发 `scr-w 800;scr-h 480;width 800;height 480`，只改 bitrate
- `VideoQuality.displayAspect()` 固定返回 800×480，`VideoActivity.videoAspect()` 用它
  → TextureView 恒为 5:3，与 800×480 坐标系、画面内容三者完全一致
- `VideoQuality.label()` 改为"流畅 2Mbps / 均衡 4Mbps / 高清 6Mbps"
- `VideoQualityTest` 更新：断言分辨率恒定、码率递增、aspect 5:3

23 项测试通过，APK 21:47 装 Mate10。**需真机确认**：各档触屏恢复且码率提升确实改善清晰度。
如果 4M/6M 在 2.4G 上卡顿，退回流畅档即可（切换无需重装）。

## 0.18 免 PIN 重连失败的真实现场 —— HiChain 绑定重认证（2026-11-20 21:29）

**上轮 0.15 的推断被日志推翻**：手机第二次连接**仍然走 op=1 身份交换**，
并非"跳过 op=1 直接 op=3"。所以 0.15 加的 `if(!identified)` 兼容分支是**死代码**，
从未触发（identified 在 op=1 后已 true）。保留无害，但不要指望它解决问题。

### 真实现场（日志 21:29:23）

```
op=1 身份交换 → 已交换身份
op=3 message=17 (STS 重认证请求)
   STS 身份检查：长度 64 字节，与已交换对端身份一致 true，与本机身份一致 false
   HiChain 消息 17：返回 0，状态 2（需继续），响应 1 条 → 我方回 STS 响应 32785
op=3 message=32896 (对端错误消息)
   HiChain 对端报告错误码：17
   HiChain 消息 32896：返回 0，状态 1（失败）
FE36 认证结束：IOException，未成功
```

对比**成功那次**（21:29:02，删了记录后）：
```
op=1 → op=3 message=1 → message=2 → message=3 → 认证成功
（message 1/2/3 = PAKE PIN 配对流程，三次握手）
```

### 结论：HiChain 绑定不对称，非应用层 bug

- 手机**有旧配对记录** → 走 **STS 重认证（message 17）** → 手机报错误码 17 拒绝我方响应。
- 手机**删了记录** → 走 **PAKE PIN 配对（message 1/2/3）** → 成功。
- STS 身份检查显示对端身份一致（deviceId 没变），问题在**双方 HiChain 绑定凭据/信任记录不匹配**：
  手机侧存了绑定，车机侧 native HUKS 的绑定记录与手机不一致或缺失。
- 我方 native 层 `AuthBusiness` 每次 `NativeAuth.create()` 新建会话，绑定持久化靠 HUKS 的
  `add_auth_info` 流程。第一次 PAKE 成功后日志里**未见 add_auth_info 报文交换**——
  绑定记录可能从未正确建立，或只建了一侧。

### 为什么暂不修（诚实）

修复点在 HiChain native 状态机（绑定记录的建立/校验），需要：
1. native 层的详细运行日志（当前 native 无日志输出，只有 JNI 层简略状态）；
2. 完整抓取 message 17/32785/32896 的报文内容做协议级比对。
当前条件（车机日志靠拍照、无 native 日志、无抓包工具）下盲改风险极高，
极可能引入新 bug 破坏已通的首次配对。**首次配对 + 投屏已验证可用，这是当前可靠基线。**

### 可行的下一步（按成本排序）

1. **短期**：接受"重连需删记录"，或做 UI 引导让用户在手机删记录（体验差但可靠）。
2. **中期**：在 native JNI 层加日志，抓一次失败的 message 17 全流程，定位错误码 17 的确切来源
   （是 add_auth_info 缺失、LT 密钥不匹配、还是身份种子不一致）。
3. **长期**：修复 native 绑定流程，让首次 PAKE 成功后正确建立双向绑定记录。

## 0.17 直连失败"临时热点创建失败，系统代码 2"（2026-11-20 21:19 日志）

用户反馈改了 0.16 后直连不行了。看 USB 手机日志：认证成功，但
`临时热点创建失败，系统代码 2` → 网络协商反复失败、无画面。

### 归因：不是 0.16 的超时改动

0.16 改的是 BSSID 探测超时（LocalHotspot/LocalApInfo/OwnApScan），这些只在**热点创建成功后**才跑。
本次失败在**创建阶段**（P2pHotspot.createGroup），与那些超时无关。

### 真正原因：快速连续重连，P2P 组没释放干净

日志时序：
```
21:18:33 本轮临时热点已移除
21:18:33 新一轮会话 token=18 开始       ← 第一次
21:18:34 正在创建热点 5220MHz
21:18:39 临时热点移除未确认，系统代码 2   ← 上一次 removeGroup 回调迟到
21:18:39 新一轮会话 token=22 开始       ← 6 秒内第二次，手动重连
21:18:39 创建 5220 → 码2 → 5745 → 码2 → 2437 → 码2（全在 21:18:39 同一秒）
21:18:39 临时热点创建失败
```
系统代码 2 = busy：上一个 Wi-Fi Direct 组还在拆除，立刻 createGroup 全被拒。
三个频段重试都在同一秒——**没有延迟，连续撞在 busy 状态上**。

### 修复（健壮性，不是回退 0.16）

`P2pHotspot.java`：
- 频段重试之间加 1.5 秒延迟（新 `startCreate()` 延迟入口），让 P2P 状态机稳定：
  `建组失败 → 1.5s 后 → startCreate()`，不再同秒连撞。
- 遗留组 `removeGroup` 成功的回调也延迟 1.5 秒再 create，并重置 `created=false`。
- `removeGroup` 失败（码2）不再直接放弃，重试最多 3 次（每次 1.5 秒）。
- 加了 cleanupRetries 字段。

23 项测试通过，APK 21:24 装 Mate10。**需真机确认**：快速连续点连接/重连时热点能稳定创建。
若仍失败，看日志是否还有同秒多频段失败；若有说明延迟不够，可加大到 3 秒。

### 对用户操作的建议

两次连接之间留 5-10 秒，别在失败后立刻反复点"开始连接"——P2P 组拆除需要时间。

## 0.16 认证后等无线网络连接慢 —— 热点探测超时优化（2026-11-20 21:12）

用户澄清："连接慢"指**首次认证通过后、等待无线网络连接那一段**，不是输码。

### 根因

热点 offer（含 SSID/密码/BSSID）的就绪依赖 BSSID 探测链，车机上这些探测大多失败，
但每次都要等满超时才降级：
- `LocalHotspot`：`degraded()` 兜底 15 秒
- `LocalApInfo`（API30+）：15 秒
- `OwnApScan`：45 秒超时 + 15 秒二次扫描

凭据里 BSSID 是可选字段（`Offer.ssidOnly` 已支持，手机主要靠 SSID+密码连热点），
所以这些等待纯属浪费——车机日志里 `本机扫描未取得热点地址` 每次都出现，每次都等满。
叠加手机认证后请求网络参数时若 offer 未好还要 `awaitNetwork(10000)` 再等 10 秒。

### 优化（缩短超时，快速降级；能快速扫到的设备不受影响，found 回调仍立即返回）

- `LocalHotspot` degraded 兜底：15 秒 → **4 秒**
- `LocalApInfo` 超时：15 秒 → **5 秒**
- `OwnApScan`：45 秒 → **8 秒**，去掉 15 秒二次扫描，只扫一次

效果：offer 从最长约 15 秒降到约 4-5 秒 deliver，网络等待显著缩短。
23 项测试全过，APK 21:12 装 Mate10。**需真机确认提速幅度且手机仍能凭 SSID-only 连入**。

## 0.15 免 PIN 重连（第二次必须删配对记录）—— 兼容修复（2026-11-20 21:05）

用户现象：**只要不是第一次连就不行**；手机弹连接窗但**不要求输码**，连不上、无画面。
这表示手机端记住了配对（免 PIN 信任重连路径），但车机端握手失败。

### 根因分析（推断，待真机确认）

`AuthBusiness.receive()` 原逻辑强制要求先收到 `op=1`（身份交换）才建会话：

```java
if((Integer)op!=3||!identified)throw new IOException("authentication order");
```

首次配对：手机发 op=1（deviceId 交换 + 弹码）→ op=3（HiChain 认证）。
**已配对手机很可能跳过 op=1，直接发 op=3 的 STS(message 17)**，因为它用已存的信任记录。
我方收到 op=3 但 `identified=false` → 抛 "authentication order" → 连不上。
表现就是"弹窗但不输码、连不上"，用户只能删记录强制回到首次 PIN 流程。

### 修复（低风险兼容，不破坏首次配对）

- `AuthBusiness.receive()`：`op=3` 且未 identified 时，若 `message==17` 且报文带 `peerAuthId`
  （hex 编码的 peer deviceId UTF-8 字节），则从中恢复对端身份、`NativeAuth.create()` 建会话，
  继续走 STS。**首次配对的 op=1 路径完全不变**。
- 新增纯函数 `peerIdFromAuthId(Object)`：hex→UTF-8 deviceId，校验可打印/长度 1..64；
  新增 `TrustReconnectTest`（往返/非法输入/边界），23 项主机测试全过。
- 加诊断日志 `认证报文：oper_type=X，message=Y，已交换身份=...,会话完成=...`：
  **下次重连失败时，把车机这条日志发我，就能确认手机第二次到底走 op=1 还是 op=3**。
- APK 21:05 构建装机。

### 诚实边界

免 PIN 重连是否成功**取决于华为手机确实用 op=3/peerAuthId 路径**，这是从现象推断的，
没有真实第二次连接的报文证据。若加装后仍失败，看新日志的 `认证报文`：
- 若第二次仍是 `oper_type=1`：手机走了身份交换但别处失败（看后续 HiChain 消息/错误码）。
- 若 `oper_type=3` 但无 peerAuthId：需要另一种身份恢复方式（可能从绑定记录反查）。
- 若 `oper_type=3` 且有 peerAuthId 仍失败：问题在 native HiChain 信任记录校验，需看 native 返回码。

### 连接速度

首次连接慢主要是扫广播 + 人工输码，中继方案另加约 1-2 秒隧道建连，非画质档可解。
免 PIN 重连若成功，第二次速度会显著提升（跳过输码）。

中继隧道全链路打通并成功出画面（20:32 中继日志：FE35/FE36 都连上并转发 267/2622 字节后

  - 高清档 1920×1080 / 6Mbps

- `MainActivity` 新增按钮"13. 视频画质：XXX（点此切换）"，循环 自动→流畅→均衡→高清→自动。

- 新增 `VideoQualityTest`（档位/排序/按频段自动/标签），22 项主机测试全过，APK 20:52 构建装机。

### 调参建议（实测时）

- 若车机是 **5G 热点**：用高清档，画质最好。
- 若车机是 **2.4G 热点**：先用均衡档；若卡顿退回流畅档；高清档在 2.4G 上大概率卡。

  这部分不是画质档能解决的。

## 0.13 手机→车机 pump 未 start 的第三个同类 bug（2026-11-20 20:04 截图）

**中继端这次真的通了**（修复 0.12 后）：Mate10 USB 日志
```
20:03:15 FE35 / FE36 监听线程已启动（true/true）
20:03:15 FE36 等待... / FE35 等待...
20:03:34 FE35 华为手机已连接，开始双向转发。     ← 手机连进来了
```
但车机日志（20:04 截图）仍是：隧道就绪、FE36 端口 5、热点 2437MHz、TCP 监听就绪，
**无 FE35 控制帧 / 认证 / H.264**。矛盾：中继转发了，车机没收到 → 断点在隧道 FE35 数据转发。

**根因（与 0.12 完全同类的第三个 bug）**：`acceptLoop` 里
```java
workers.add(new Thread(() -> pump(fromPhone, toCar, ...)));  // 手机→车机方向，new 了没 start
pump(fromCar, toPhone, ...);  // 只有车机→手机方向在跑，阻塞空等
```
手机→车机的 pump 线程从未启动，所以手机发的 FE35 字节根本没写进隧道。

**修复**：显式 start + 转发字节计数日志：
```java
Thread toCarThread = new Thread(() -> pump(fromPhone, toCar, ...), "relay-FE35-up");
workers.add(toCarThread); toCarThread.start();
```
pump 每累计 4096 字节打一条 `XXX 已转发 N 字节`，便于确认数据真的在流动。
已审查 RelayActivity 全部 new Thread：boot / fe36Accept / fe35Accept / toCarThread 均有对应 start()。
21 项测试通过，APK 20:13 装 Mate10。

**下次联调判据**：中继日志除三行启动标志外，还应出现 `FE35->车机 已转发 N 字节`；
车机日志应出现 `FE35 控制帧：类型 X`（隧道路径的 protocolReceive 会打这个，虽然没有"FE35 收到连接"那行——
那行只在 acceptProtocol 里，隧道模式不走它）。**注意**：车机端"无 FE35 收到连接"是正常的，
不要误判为失败，要看有没有 FE35 控制帧 / 认证 / H.264。

## 0.12 中继线程未 start 的第二个 bug（2026-11-20 19:36 车机截图）

用户发来两张车机日志（19:36/19:37）+ USB 中继日志（19:33/19:35）。

### 车机日志（两张一致）
```
19:33:12 隧道服务端已就绪（等待中继手机连接）
19:33:17 已从中继取得 FE36 端口 5          ← 隧道控制面通了
19:33:32 本轮热点已就绪 2437 MHz（2.4 GHz）
19:33:32 本轮热点的三个 TCP 监听已就绪；尚未收到手机网络连接
（全程无 FE35/FE36 收到连接 / HiChain 认证成功 / 收到 H.264）
```
即：隧道连上了、FE36 端口传到了车机、热点建好了，但**手机到中继的 FE35/FE36 没建立**。

### 中继日志（USB）
```
19:33:14 连接车机隧道服务 7E:34:46...
19:33:14 中继 FE36 端口 5 已通过隧道告知车机
19:33:15 中继已就绪：等待华为手机连接 FE35/FE36
19:33:15 FDEE 广播已启动
（没有 FE35 等待... / FE36 等待... 两行）
```

### 根因：0.10 的"修复"引入了新 bug —— 线程从未 start

0.10 把两路 acceptLoop 从串行改成"分别放线程"，但写成了：

```java
workers.add(new Thread(() -> acceptLoop(...)));   // 只创建 Thread 对象并存入列表
workers.add(new Thread(() -> acceptLoop(...)));   // 从未调用 .start()
```

`new Thread()` + `add()` **不会启动线程**，两路 FE35/FE36 监听根本没运行。这就是中继日志里
始终没有 `FE35 等待...`/`FE36 等待...` 两行、手机连不进来的真正原因。
（设备 APK 已核对为最新版、含 `relay-accept-fe35/36` 字符串、MD5 与本地一致——不是版本问题，
是代码本身漏了 start。）

### 修复

```java
Thread fe36Accept = new Thread(() -> acceptLoop(...), "relay-accept-fe36");
Thread fe35Accept = new Thread(() -> acceptLoop(...), "relay-accept-fe35");
workers.add(fe36Accept); workers.add(fe35Accept);
fe36Accept.start(); fe35Accept.start();              // ← 关键：真的启动
log("FE35 / FE36 监听线程已启动（true/true）。");     // 自检日志
```

21 项测试通过，APK 已重建装到 Mate10（19:48+）。**下次联调判据**：中继日志必须出现
`FE35 / FE36 监听线程已启动（true/true）` + 随后两行 `FE35 等待...`/`FE36 等待...`。

## 0.10 弹码成功但无画面 —— 中继 FE35 监听 bug（2026-11-20 14:36 照片 + 17:30 修复）

用户实测：华为手机成功弹出连接码、输码，但车机无画面。三张照片 + 中继手机 trace 定位如下。

### 证据链

- 车机端照片：隧道服务端就绪、`已从中继取得 FE36 端口 5`（隧道控制面通了）、热点 2437 MHz
  就绪、BSSID 有效、三个 TCP 监听就绪，但**从未出现** `FE35 收到连接` / `FE36 收到连接` /
  `HiChain 认证成功` / `收到手机 TCP 连接`。随后 `TCP 监听结束：I/O 错误`×3、`连接已断开`
  （这是 stopInternal 关闭 socket 的正常清理日志，不是根因）。
- 中继手机 trace：`中继已就绪：等待华为手机连接 FE35/FE36`、`FE36 等待华为手机连接...`、
  `FDEE 广播已启动`，但 `开始双向转发` **出现 0 次** —— 中继的 FE35/FE36 从没收到华为手机连接。
  手机弹码很可能是连到了系统 `com.huawei.nearby` 自己的 FE36，没走到我们的中继。

### 根因（明确的代码 bug）

`RelayActivity.start()` 里两路 acceptLoop 串行调用：

```java
acceptLoop(business, fe36Link, token, "FE36");   // 内部 while: server.accept() 阻塞，永不返回
acceptLoop(control, fe35Link, token, "FE35");    // 永远执行不到
```

`acceptLoop` 是阻塞循环，FE36 一行把启动线程占死，**FE35 的 RFCOMM 监听根本没启动**。
华为手机连 FE35 控制通道时无人应答 → 卡在弹码、认证无法继续 → 无画面。
中继 trace 全程只有 `FE36 等待...`、从无 `FE35 等待...` 正好印证。

### 修复

两路 acceptLoop 各放进独立线程：

```java
workers.add(new Thread(() -> acceptLoop(business, fe36Link, token, "FE36"), "relay-accept-fe36"));
workers.add(new Thread(() -> acceptLoop(control, fe35Link, token, "FE35"), "relay-accept-fe35"));
```

21 项主机测试通过、APK 已构建（17:29 装到中继手机）。此机单测时因车机隧道服务端未启动，
中继在 `连接车机隧道服务` 就 IOException（预期，需车机配合）。**修复本身需两真机联调最终确认**。

### 车机 WLAN/热点不能同时开的说明

用户指出车机 WLAN 与热点不能同时打开。当前设计里车机建 LocalOnlyHotspot（AP），手机连该 AP 后用
client IP 与车机 owner IP 的 TCP 监听通信——这条链路不要求车机同时连别的 WLAN，理论上兼容。
车机照片也证实热点 + BSSID + TCP 监听都就绪。本次无画面的直接原因是中继 FE35 没监听（上面已修），
不是热点链路；但若修复后仍无画面，下一步要重点查手机是否真的连上了车机热点、是否拿到 client IP。

## 0.9 路线 B：中继透明隧道（车机仍是真接收端）

用户选择路线 B：用一台有 BLE 广播的安卓手机做中继，站在无广播车机前面；车机保持真接收端，
HiChain 密钥、协议栈、热点、投屏全在车机，中继只搬运蓝牙 FE35/FE36 字节。

### 架构（端到端拓扑）

```
华为手机  ──BLE广播发现 + FE35/FE36 蓝牙──▶  中继手机（有广播，如 OnePlus）
                                                   │
                                          蓝牙 RFCOMM 隧道（私有 UUID 7d3a1c62…，预配对）
                                          复用 FE35/FE36 两路字节 + 控制帧
                                                   │
                                                   ▼
                                        车机（无广播，真接收端）
                                          认证/网络/视频全在此
                         认证后：车机开 2.4G 热点 ──▶ 华为手机直连投屏（中继不碰视频）
```

关键洞察（来自代码探查，不是推测）：
- **认证与蓝牙 MAC 无关**：身份 = 车机随机 HUKS 种子 + 手机 JSON 里的 deviceId + 六位连接码
  （`ReceiverEngine.java:98-110,137`、`AuthBusiness.java:78-79`）。所以手机连中继的 MAC 不影响 HiChain。
- `TestSession.select()`（`ReceiverEngine.java:92-96`）只是"同一会话单一 MAC"准入过滤，中继拓扑下自洽。
- **隧道只覆盖蓝牙阶段**：认证成功后手机连车机热点走 TCP/UDP 投屏（`receiveTcp`、`HiSightClient`），
  中继不在数据路径上。车机必须能开热点且手机能连上——这台车机自检已证实 2.4G 热点 + 有效 BSSID。
- `NearbyWire.Negotiator`（`NearbyWire.java:66-86`）会把 FE36 的 RFCOMM channel 编进回复告诉手机；
  隧道模式下必须回**中继注册的 channel**，故中继通过控制帧 `fe36_channel` 告知车机。

### 新增/改动代码

- `TunnelProtocol.java`（新）：隧道帧 `[0x5A][ch][len:2][payload][crc16:2]`，ch0=控制 / ch1=FE35 / ch2=FE36，
  CRC-CCITT，流式 Decoder 支持分片与多帧粘连、CRC 校验失败即丢弃。
- `TunnelLink.java`（新）：WireLink（in/out/peer/close 抽象）+ BtLink（本地蓝牙）+ Link（隧道逻辑链路）

- `ReceiverEngine.java`：`clients` 从 `BluetoothSocket` 泛化为 `WireLink`；`acceptProtocol` 拆出公共
  `admitLink`；`protocolReceive` 改吃 WireLink。新增 `startTunnelProtocol`（车机端隧道服务端）：

- `RelayActivity.java`（新，中继角色 UI）：连车机 TUNNEL_UUID → 建 Mux → 注册 FE36/FE35 本地 RFCOMM
  接受华为手机 → 双向 pump 字节 ↔ 隧道逻辑链路 → 广播 FDEE（与车机同 payload）→ 把中继 FE36 channel
  经控制帧告知车机。
- `MainActivity.java`：诊断页新增"11. 中继隧道（车机端）开关"和"12. 进入中继转发（有广播手机用）"。

- `TunnelTest.java`（新，已注册进 test-host）：帧编解码、分片、粘连、CRC/长度/魔数拒绝、200 轮随机 fuzz，

### 0.8.2 新增第 10 项「BLE 扫描独立自检」

- 多份报告反复出现 `本轮使用本机蓝牙地址派生身份`，而 HUKS 是在进程启动时用原始
  seed 注册的。认证时 `self_auth_id` 用了派生值，与密钥库身份不一致，HiChain 会拒绝 PIN，

2. **认证身份与 HUKS 种子强制一致**：`start()` 不再用 `WireIdentity.select()` 的结果作为

   不是协议认证结论。可用 `identity` 里的 `beacon_extended=false` 退回 11 字节。
4. **允许同一次 FE36 连接内重新交换身份**：手机每次重输连接码都会重发 op=1，
   旧代码直接抛 `identity state` 断开连接，形成"输一次码断一次"的循环；现在会关闭旧

5. **清理遗留 Wi-Fi Direct 组**：20:30 真机复测抓到 `已有 Wi-Fi Direct 连接，实验未修改它`，

## 0.5 长时间断线与重连修复（23:02 实测稳定）

1. **30 秒误断**：`22:49:35 TCP 阶段 2 结束：SocketTimeoutException`。DMSDP 控制通道的空闲判定

   之前"允许重复 op=1"的实现会重建 HiChain handle，导致第一次握手的 STS 上下文失效，
   手机回错误码 17，认证失败，手机端把状态记为坏配对，只能删记录重配。
   修复：重复 op=1 时幂等应答同一身份，不重建会话、不更换身份或连接码。

## 1. 现象与代码根因

| 现象 | 直接原因 | 位置（0.11.1） |
| --- | --- | --- |
| 发送端搜不到、不弹 HiCar 提示 | BLE 发现广播只在热点准备成功后才启动。Android 8.1 上热点一定失败，所以广播从未发出 | `ReceiverEngine.start()`：`startFdeeAdvertising` 只作为 `P2pHotspot.Events.ready()` 的回调执行 |
| 车机发不出广播 | `P2pHotspot.start()` 第一行 `if (Build.VERSION.SDK_INT < 29) { events.failed(...); return; }`，而 `start()` 里 `SDK>=33` 才用 `LocalHotspot`，8.1 走的一定是 `P2pHotspot` | `P2pHotspot.java:22`、`ReceiverEngine.java:131` |
| 只有 2.4G 热点时连不上 | 频段掩码只登记 5G 九个信道，`NetworkResource.Offer` 对 2.4G 直接抛 `unverified AP offer` | `NetworkResource.frequencyMask()`、`Offer` 构造器 |
| 2.4G 上热点也建不起来 | `LocalHotspot` 硬编码信道 149（`channels.put(2,149)`），并要求系统回读信道必须仍是 149；Android 8/9 根本没有这套接口 | `LocalHotspot.start()/inspect()` |
| 点“开始连接”后完全没有反应 | `HomeActivity` 必须等 `ACTION_REQUEST_DISCOVERABLE` 返回大于 0 才启动服务；车机常直接拒绝或根本不弹窗 | `HomeActivity.onActivityResult()` |

三个现象是同一条因果链：**热点失败 → 广播不启动 → 手机搜不到 → 不弹窗**。
因此修复的核心是**把“被发现”与“能投屏”解耦**。

## 2. 改动清单

### 2.1 发现广播不再依赖热点（关键）

`ReceiverEngine.start()` 现在按顺序做三件事，互不阻塞：

1. 注册 FE35 / FE36 的 RFCOMM 监听；
2. 立即启动 FDEE BLE 广播；
3. 并行准备热点，失败只记录原因，不结束会话。

热点失败时状态栏会显示具体原因（例如“系统禁止热点”“没有可用信道”），手机仍能发现本机并完成蓝牙认证，
日志能明确指出卡在哪一步。

BLE 广播本身也加了兼容回退：可连接模式失败时改用不可连接模式重试一次，并统一使用高发射功率。
若系统根本没有 `BluetoothLeAdvertiser`（部分车机蓝牙只有经典模式），会直接说明“这台设备无法被手机发现”，
而不是静默失败。

### 2.2 2.4G 支持

`NetworkResource.frequencyMask()` 在原有 9 个 5G 信道之后追加了 2.4G 的 1–13 信道，
**5G 的位序保持不变**（这部分是线上协议可见的）。`Offer` 因此接受 2.4G 频点，
协商时手机上报的频段掩码与本机实际信道取交集。

协商失败不再是无提示的 `accepted=false`，而是写入可读原因，例如
“手机上报的可用频段不包含本机热点信道 2437 MHz（本机为 2.4 GHz 热点）”。

### 2.3 热点创建按版本分流

`LocalHotspot` 重写为 Android 8.0 起可用：

| 系统 | 接口 | 名称/密码来源 | 信道来源 |
| --- | --- | --- | --- |
| Android 11+ | `startLocalOnlyHotspot(SoftApConfiguration, Executor, Callback)` | 配置回读 | 配置回读，或 SoftAp 状态回调 / 本机扫描 |
| Android 8.0–10 | `startLocalOnlyHotspot(Callback, Handler)` | `getWifiConfiguration()` 回读 | 本机扫描；取不到时按 2437 MHz 上报并在日志说明 |

Android 11+ 的热点配置同时列出 `BAND_2GHZ:2437` 与 `BAND_5GHZ:5745`，由系统按芯片能力选择；
系统若拒绝双频请求，会依次退回“只请求 2.4G”“只请求 5G”。不再强制 149 信道。

`P2pHotspot`（Android 10 的 Wi-Fi Direct 路径）同样先试 5745，建组失败自动退到 2437。

### 2.4 地址与信道的降级顺序

1. 系统配置回读（Android 11+）；
2. SoftAp 状态回调（`registerLocalOnlyHotspotSoftApCallback`，反射调用，失败不影响流程）；
3. 本机扫描本轮 SSID（`OwnApScan`，放宽为“同 SSID、任意频段”，并回报观测到的信道）；
4. 兜底：地址取本机 Wi-Fi 接口硬件地址，信道按 2437 MHz，并在日志注明“未经扫描核验”。

第 4 步才使用仅 SSID 的凭据格式（`Offer.ssidOnly`，BSSID 为空）。

### 2.5 启动流程不再被系统弹窗拦截

`ACTION_REQUEST_DISCOVERABLE` 改为“尽力而为”：车机拒绝、不弹窗、甚至抛异常时，
接收服务照常启动，只写一条日志。经典蓝牙可发现只影响别的设备主动搜索经典蓝牙，
不影响 FDEE 的 BLE 广播。

`MainActivity` 的网络实验门槛从 `SDK >= 29` 降到 `SDK >= 26`。

### 2.6 其他 8.1 兼容性

- 通知“停止”按钮改用资源图标。部分 Android 8/9 SystemUI 在展开 `Icon == null` 的通知动作时会崩溃。
- RFCOMM 端口读取失败不再直接结束会话，改为继续广播并提示“业务通道未取得”，便于定位。
- 原生库加载失败会记录异常类型、进程位数与 `SUPPORTED_ABIS`，便于判断是否 32 位 ABI 不匹配。

## 3. 自检入口

“设置与诊断”新增两项，用来区分“广播问题”和“热点问题”：

- **7. 发现广播自检（FDEE，30 秒）**：只发 FDEE 广播，报告系统是否提供 `BluetoothLeAdvertiser`、
  是否支持多路广播，以及广播启动成功/失败码。手机搜不到而这里成功，问题在手机侧；
  这里失败，问题在车机蓝牙。
- **8. 热点能力自检（读取实际信道，30 秒）**：创建一次临时热点，报告系统实际采用的信道与频段，
  然后释放。可直接确认这台车机到底给的是 2.4G 还是 5G。

## 4. 预期日志顺序（8.1 正常路径）

```
FDEE 实验开始：型号 00048000，序号 N；未验证手机识别。
FE35 / FE36 已注册；动态业务端口 7，等待手机连接。
FDEE 广播启动成功：11 字节 service data（可连接）；这不是 HiCar 连接成功。
请求本地热点（Android 8/9 兼容接口，由系统决定名称与信道）；不记录名称或密码。
系统返回的本轮热点名称与密码已读取；Android 8/9 不提供热点地址与信道，稍后按本机扫描或默认值处理。
本轮热点已就绪：2437 MHz（2.4 GHz）；开始等待手机入网。
FE35 收到连接；对端尚未认证。
已交换实验身份，等待 HiChain 认证；请使用页面显示的六位连接码。
HiChain 后端报告认证成功；等待后续网络及媒体会话，认证成功本身不代表投屏成功。
网络协商：类型 4，响应 N 字节；角色已协商 true，临时凭据已发送 true。
收到手机 TCP 连接：阶段 2（0 网络控制，1 DMSDP 入口，2 DMSDP 控制）。
```

若日志停在“FDEE 广播启动失败”，是车机蓝牙不提供 BLE 外设广播，与本项目无关，需要换蓝牙方案。
若停在“本轮热点已就绪”之后没有“FE35 收到连接”，说明手机虽然搜到了但没有发起连接，
通常与手机端 HiCar 记录、配对状态或型号识别有关。

## 5. 仍需实测确认

- 32 位进程下车机能否加载 `armeabi-v7a` 原生库（本版未改原生库）。
- 车机 `BluetoothLeAdvertiser` 是否可用、是否支持可连接广播。
- 车机本地热点是否允许普通应用创建（部分厂商 MDM 策略会禁止）。
- 2.4G 链路的实际带宽能否承载 800×480 H.264 + AAC。协议层不再拦 2.4G，
  但 2.4G 的吞吐和干扰是物理限制，画面可能卡顿或手机主动降低码率。
- Android 8/9 上 BSSID 只能靠本机扫描或接口硬件地址推测；若手机要求严格匹配，
  连接会停在入网阶段，日志会显示“仅 SSID 方式上报”或“未经扫描核验”。
